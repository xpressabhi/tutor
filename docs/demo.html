Calibration 1 — type vs interface

rung 2

QWhy would you reach for one over the other — and is there anything you can do with one that you can’t do with the other?

A“both ar emore of less same, but you can to union or intersection with interfaces but with type you can do”

partialHeadline (“more or less the same”) is right for object shapes; union/intersection association is present but garbled and possibly inverted (interfaces cannot declare unions); no mention of declaration merging or the extends-equivalence, which is what screens actually listen for.

taughtinterface cannot declare a union — type Status = "on" | "off" has no interface form. Intersection is not a clean separator: type C = A & B ≡ interface C extends A, B {} for object shapes. The clean separators: declaration merging (interface-only) and non-object aliases (tuples, primitives, functions, conditional/mapped types — type-only). Rule of thumb: interface for object contracts; type the moment you need a union or a non-object alias.

Q"A" / setTimeout(() => "B", 0) / Promise.then(() => "C") / "D" — exact order, and why?

A“A, D, C, B”

QWhy? (right answer, unexplained — probe sent on the spot, before any verdict)

A“A => it comes first / D => it comes last in code but on stack it will be after B and C, B will be added to callback queue and C will be added to microtask queue / C=> microtask queeu will be processed / B => at last callback queue will be processed”

partialOrder correct; core mechanism right (microtask queue drains before callback queue); but the D explanation is muddled/wrong — D runs synchronously before anything queued executes; also missing that the microtask queue drains fully before the next macrotask.

taughtSync pass runs to completion → ALL microtasks drain (including ones queued by microtasks) → next macrotask. await continuations live in the same microtask queue. Re-probe later with an await-continuation framing.

Calibration 4 — async iteration: the miss-and-recover arc

past the middle  ·  wrong → teach → re-ask ×3 → correct

12:32 calibration 4

QAn async generator yielding 1 and 2, consumed with for await (const x of count()) — what prints? Kicker: what happens with a plain for...of, and why?

A“it will print {value:1, done:false} {value:2, done:true} once you replace with plain for ....of , i guess it will not traverse oover count interator, but ideally it should”

wrongTwo mechanics misses, both (verified) by running the code: (a) loops never expose {value, done} — that only appears when calling next() by hand; (b) with no return here, the second result is {value:2, done:false}, not done:true. The kicker is half right — but a plain for...of throws TypeError: ... not iterable before the first iteration, because an async generator implements Symbol.asyncIterator only.

taughtLoops bind result.value; done never surfaces; return values are silently dropped. Two protocols: sync iterables expose [Symbol.iterator]; async iterables expose [Symbol.asyncIterator] whose next() returns a promise. for await exists because for...of cannot wait.

Q(re-ask, rung 2, fresh framing — never the identical question) function* gen() { yield 1; yield 2; return 3; } consumed with plain for (const x of gen()) — what prints? Does the 3 show up?

A“ok I will print 1,2 then 3”

wrongExpects the return value to appear in loop output. Teaching: the desugaring — for...of is r = it.next(); while (!r.done) { body(r.value); r = it.next(); }. When {value: 3, done: true} arrives, the guard fails and the value is discarded before the body ever sees it. One-line rule: yield produces values for iteration; return ends it.

Q(re-ask, minimal-change task) Edit the generator so the loop prints 1, 2, 3.

Achanged return 3 → yield 3.

correctFix verified correct (verified) — node prints 1, 2, 3; minimum change made. Why-probe: “both return value as 3, the difference is at done, with yield done will be false, at next step value will be undefined and done will be true” — the done-flag model, stated cleanly.
